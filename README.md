# amr-ros2-slam

**ROS 2 기반 2D LiDAR SLAM + 센서 퓨전 자율주행 AMR (엔코더 없는 4WD)**

기존 아두이노 스마트카를 구동부로 재활용하고 라즈베리파이 5 + LiDAR를 상위 제어기로 올려, ROS 2 환경에서 SLAM 지도 작성과 자율주행을 구현하는 프로젝트입니다.

이전 프로젝트([amr-control](#관련-프로젝트))에서 정립한 **상위(판단) / 하위(구동) 계층 분리** 설계를 그대로 계승합니다.

> **현재 상태** — 실주행 SLAM 지도 작성 완료, Nav2로 장애물을 회피하며 단일 목표 지점까지 자율주행 성공 (태그 `nav2-v1-success`).
> 다음 단계: 축소 물류센터 환경에서 다지점 순회.

## 시스템 구성

```
[RPLIDAR A1M8] ──USB──┐
                      ▼
[Raspberry Pi 5 / Ubuntu 24.04 + ROS 2 Jazzy]                ← 판단 계층
   sllidar ──► rf2o (라이다 오도메트리) ──┐
                                          ├──► EKF (robot_localization) ──► AMCL / slam_toolbox ──► Nav2
   amr_bridge (C++) ──► /imu ─────────────┘
          │ USB Serial (커스텀 패킷 프로토콜)
          ▼
[Arduino UNO]                                                ← 구동 계층
   ├─ L298N ──► DC 기어모터 ×4 (4WD, 엔코더 없음)
   ├─ MPU-6050 (I2C, 자이로 Z축 40Hz)
   └─ HC-SR04 초음파
```

| 계층 | 하드웨어 | 역할 |
|---|---|---|
| 상위 | Raspberry Pi 5 (4GB) | SLAM, 위치추정, 경로계획, 센서 퓨전 |
| 하위 | Arduino UNO | 모터 구동, 센서 읽기, 워치독 안전 정지 |
| 시각화 | 개발용 PC (WSL2) | RViz2 원격 실행 |

### TF 트리

```
map ──(AMCL / slam_toolbox)──► odom ──(EKF)──► base_link ──(static)──► laser
                                                         └─(static)──► imu_link
```

EKF 입력: rf2o → `x, y, yaw` / IMU 자이로 → `vyaw` (각 센서가 잘 측정하는 축만 선택 융합)

## 소프트웨어 구성

### 하드웨어 인터페이스 노드 — `amr_bridge` (C++)

프로젝트 1의 패킷 계층을 C++로 포팅해 재사용하고, 통로만 블루투스 → USB 시리얼(termios)로 교체했습니다.

- `/cmd_vel` → 차동 구동 변환 → 데드존 보상 → 연속 PWM 패킷(0x15) 20Hz 송신
- **회전-후-직진 중재**: 곡선 명령을 "제자리회전" 또는 "직진"으로 변환 (아래 설계 판단 참고)
- 아두이노 센서 패킷 수신 → `/ultrasonic`, `/current`, `/imu` 발행
- 명령 끊김 시 자동 정지(cmd_timeout), 아두이노 측 워치독과 이중 안전장치

### 시리얼 패킷 프로토콜

형식: `[STX 0x02][LEN][CMD][DATA…][CHK][ETX 0x03]` — 수신 측은 LEN으로 패킷 길이를 분기

| 방향 | CMD | 길이 | 내용 | 체크섬 |
|---|---|---|---|---|
| Pi → Arduino | 0x10~0x14 | 5B | 전진/후진/좌/우/정지 (프로젝트 1 호환) | LEN^CMD |
| Pi → Arduino | 0x15 | 7B | 연속 PWM (좌, 우 int8) | LEN^CMD^L^R |
| Pi → Arduino | 0x30 | 5B | 하트비트 | LEN^CMD |
| Pi → Arduino | 0x40 / 0x41 | 5B | 경고 ON / OFF | LEN^CMD |
| Arduino → Pi | 0x20 / 0x21 | 6B | 거리 / 전류 (1B) | LEN^CMD^DATA |
| Arduino → Pi | 0x22 | 7B | 자이로 Z (int16) | LEN^CMD^HI^LO |

새 명령을 추가해도 기존 5바이트 명령 경로는 한 줄도 수정하지 않는 구조입니다.

## 설계 판단 기록

### Ubuntu Server 선택 (Desktop 대신)

| 항목 | Desktop | Server |
|---|---|---|
| 부팅 직후 RAM | ~1.2 GB | ~300 MB |
| GUI | 있음 | 없음 |

- **리소스 배분** — 4GB 보드에서 확보한 약 900MB를 SLAM/Nav2 연산에 배분
- **표현/연산 계층 분리** — RViz2는 개발 PC에서 원격 실행, Pi는 센서 처리와 SLAM에 집중. 실주행 시 로봇에 모니터를 부착할 수 없으므로 구조적으로도 필연적인 선택
- **프로젝트 1 설계 원칙 계승** — 상위/하위 분리와 동일한 사고를 시각화/연산 축에 적용

### ROS 2 Jazzy 선택 (Kilted / Lyrical 대신)

- Ubuntu 24.04 LTS와 페어링되는 LTS 배포판 (EOL 2029-05)
- Nav2, slam_toolbox 등 주요 패키지의 레퍼런스·사례가 가장 두터움
- 국내 로봇·장비 업계 실사용 비중 고려

### 오도메트리: LiDAR-only → LiDAR + IMU 센서 퓨전

엔코더가 없어 처음에는 라이다 오도메트리(rf2o)만으로 진행했습니다.

- **문제 규명** — 좁은 실내에서 제자리회전을 시키면 rf2o 추정 자세가 원위치로 되돌아가는 현상을 실측으로 확인. 진동·QoS·네트워크 가설을 하나씩 배제한 뒤 rf2o의 회전 추정 실패로 확정
- **해결** — MPU-6050 자이로를 추가하고 robot_localization EKF로 융합
- **축 선택** — 처음엔 rf2o의 yaw를 완전히 제외했으나 자이로 적분 오차가 누적(slam 보정량 28.8°). rf2o yaw를 다시 넣어 두 센서가 서로의 약점을 보완하게 하자 보정량 0.4°로 감소
- **교훈** — 특정 축에서 약한 센서를 배제하는 것이 아니라, 가중 융합하는 것이 센서 퓨전의 본래 취지

### 개루프 구동 캘리브레이션

엔코더가 없어 `cmd_vel(m/s)` → PWM 변환을 실측으로 구했습니다.

- 선형회귀 `v = 0.002442 × int8 + 0.0315` (R² = 0.985), 최고속도 약 0.345 m/s
- 최소 구동값(데드존) int8 80 — **유효 구동 범위가 int8 80~127, 47단계뿐**
- 결과적으로 **곡선 주행과 저속 주행이 물리적으로 불가능**

### 곡선 불가 → 회전-후-직진 중재

Nav2 컨트롤러(Regulated Pure Pursuit)는 곡선 주행을 전제로 속도 명령을 냅니다. 이 로봇은 곡선을 못 하므로, 브릿지가 명령을 로봇이 실제로 할 수 있는 두 동작으로 번역합니다.

- 회전 요구가 크면 → **멈추고 제자리회전**
- 회전 요구가 작으면 → **회전 성분을 버리고 직진**
- Nav2는 매 주기 위치를 다시 보고 명령을 갱신하므로, 결과적으로 "멈춤 → 회전 → 직진"의 꺾은선 주행이 됨
- Nav2 쪽은 Rotation Shim Controller로 큰 방향 전환을 제자리회전으로 처리

하드웨어 제약을 상위 계층(Nav2)이 아닌 하드웨어 인터페이스 계층에서 흡수한 설계입니다.

### Nav2 튜닝 핵심

| 항목 | 설정 | 이유 |
|---|---|---|
| 전역 / 지역 코스트맵 inflation | 0.25 / 0.12 로 분리 | 경로는 통로 가운데로, 충돌 검사는 실제 크기 기준으로 |
| AMCL 갱신 조건 | 이동량 0 이상이면 갱신 | 정지 순간의 깨끗한 스캔으로도 보정 |
| 구동 방식 | 짧게 가고 멈추기 반복 | 정지 구간에 위치추정 보정 시간 확보 |
| 플래너 허용오차 | 0.1 m | 목표에 못 갈 때 "가짜 도착" 방지 |
| 정지 판정 / 회전 가속 한계 | 낮춤 / 높임 | 작은 회전 명령이 정지로 잘리는 교착 방지 |

## 트러블슈팅 기록

증상 → 측정 → 원인 → 수정 순서로 해결한 주요 문제들입니다. 상세 과정은 `docs/`의 단계별 기록에 있습니다.

| 증상 | 원인 | 해결 |
|---|---|---|
| 정지 상태인데 EKF yaw가 초당 4.5°씩 흐름 | IMU 메시지 공분산 [0]=-1 → ROS 규약상 각속도 전체가 무효 처리됨 | 미사용 축은 큰 분산값으로 표현 (드리프트 200배 개선) |
| 매핑은 정상인데 Nav2에서는 반대로 주행 | 라이다 장착 방향(TF yaw) 180° 오류. 매핑은 일관되게 돌아간 지도를 만들어 문제를 가림 | TF 수정 후 재매핑 |
| 주행 중 회전 추정이 계속 틀어짐 | IMU가 세로로 장착돼 자이로 Z축이 수평을 향함 (장착 후 재검증 누락) | 수평 장착 + 부호 보정 |
| 경로는 장애물을 피하는데 로봇은 장애물로 직행 | 브릿지가 좌우 바퀴를 각각 데드존 보상 → 좌우 비(곡률) 소실, 곡선이 직진이 됨 | 회전-후-직진 중재 |
| 회전 명령이 계속 나오는데 로봇이 정지 | 가속 제한 제어기(현재속도+가속×주기)와 정지 판정 데드존의 교착 | 정지 판정 하향, 가속 한계 상향 |
| 목표에서 70cm 떨어진 곳에서 "도착" | 플래너 허용오차 0.5로 대체 목표 생성, 컨트롤러는 경로 끝점 기준 판정 | 허용오차 0.1 |
| 주행 중 위치 상실 | AMCL이 이동 중(스캔 1장 찍는 동안 11° 회전한) 뭉개진 스캔으로만 보정 | 정지 구간 스캔으로도 보정 |
| Nav2 일부 노드 inactive로 남음 | Pi 부하로 라이프사이클 응답 타임아웃 | bond_timeout·기동 지연, 수동 활성화 절차 |

## 알려진 한계와 개선 방향

- **복도 문제** — 벽과 나란히 직진할 때 라이다만으로는 앞뒤 이동량 판단이 어려워 위치추정이 밀릴 수 있음
- **정밀 정지 한계** — 최저속도가 고정이라 감속 정지가 불가, 목표 근처 오버슛 가능
- **개선 1순위: 휠 엔코더** — 바퀴 회전량을 직접 측정해 위 두 한계를 근본적으로 해결
- 환경 측면에서는 진행 방향 앞뒤로 특징물이 보이도록 배치해 완화

## 실행 방법

```bash
# 1) 라이다 단독 선기동 (Nav2와 동시 기동 시 초기화 타임아웃이 발생해 분리)
ros2 launch sllidar_ros2 sllidar_a1_launch.py serial_port:=/dev/rplidar frame_id:=laser

# 2-a) 매핑 (teleop으로 주행)
ros2 launch ~/ros2_ws/launch/amr_mapping_nolidar.launch.py turn_gain:=5.0

# 2-b) 자율주행 — 로봇을 매핑 시작 위치·방향에 놓고 실행
ros2 launch ~/ros2_ws/launch/amr_nav2_nolidar.launch.py
```

RViz2는 개발 PC에서 실행합니다 (Fixed Frame `map`).
